# 10 — استقرار و عملیات

## 1. هدف

محیط توسعه، staging و production باید از نظر اسرار، دیتابیس و سرویس‌های بیرونی جدا باشند. اجرای محلی در Termux صرفاً محیط توسعه/بررسی است و به‌تنهایی اثبات‌کننده آمادگی production نیست.

## 2. محیط‌ها

| محیط | هدف | داده مجاز |
|---|---|---|
| Local | توسعه و تست | داده ساختگی |
| Staging | آزمون یکپارچگی و پذیرش | داده ساختگی یا ناشناس‌شده |
| Production | سرویس واقعی | فقط داده مجاز طبق سیاست مصوب |

هیچ secret یا credential بین محیط‌ها مشترک نباشد، مگر با توجیه و کنترل مستند.

## 3. الزامات runtime

محل استقرار باید از موارد زیر پشتیبانی کند:
- اجرای امن Next.js App Router و Route Handlerهای Node.js.
- اتصال TLS خروجی به Provider و Supabase.
- مدیریت environment secrets بدون قرارگیری در bundle.
- timeout و محدودیت منابع قابل تنظیم.
- مشاهده log و metric بدون ثبت محتوای محرمانه.
- تعیین IP واقعی درخواست فقط از headerهای proxy مورد اعتماد.
- deployment rollback و health check.
- کنترل منطقه پردازش و محل نگهداری داده متناسب با سیاست دفتر.

انتخاب پلتفرم هنوز قطعی نیست. Vercel، میزبانی Node.js مدیریت‌شده و VPS باید بر اساس دسترس‌پذیری از ایران، محدودیت پرداخت، latency، پایداری، پشتیبانی runtime و شرایط قراردادی مقایسه شوند. انتخاب صرفاً بر اساس سهولت deploy مجاز نیست.

## 4. کنترل Provider

- درخواست‌ها از سرور ارسال می‌شوند.
- timeout و سقف خروجی محدود است.
- مدل از تنظیمات سرور خوانده می‌شود.
- خطاهای transient فقط با سیاست retry محدود و بدون تکرار پرهزینه مدیریت می‌شوند.
- kill switch مستقل از UI امکان توقف درخواست جدید را می‌دهد.
- health check نباید درخواست پرهزینه به مدل بفرستد.

## 5. سیاست داده OpenAI

بر اساس مستندات فعلی OpenAI:
- API data به‌طور پیش‌فرض برای آموزش مدل استفاده نمی‌شود مگر opt-in صریح.
- Responses API در حالت عادی application state را تا ۳۰ روز نگه می‌دارد؛ برای درخواست foreground با store:false این application state ذخیره نمی‌شود.
- abuse monitoring logs به‌طور پیش‌فرض ممکن است تا ۳۰ روز نگهداری شوند.
- store:false به‌تنهایی معادل Zero Data Retention نیست.
- قابلیت‌های خاص مانند background mode، فایل‌ها، تصویر و سرویس‌های ثالث می‌توانند استثناهای retention داشته باشند.

بنابراین MVP از متن ساده، foreground request و store:false استفاده می‌کند و فایل/تصویر/ابزارهای میزبانی‌شده را فعال نمی‌کند. داده پرونده و اسرار موکل تا تصویب ارزیابی جداگانه ارسال نمی‌شوند. سیاست باید پیش از انتشار با شرایط واقعی حساب و endpoint دوباره تطبیق داده شود.

مرجع: https://developers.openai.com/api/docs/guides/your-data

## 6. محدودیت جغرافیایی و دسترسی Provider

فهرست رسمی کشورهای پشتیبانی‌شده OpenAI API باید پیش از هر استقرار دوباره بررسی شود. در بررسی مورخ 2026-11-04، ایران در فهرست کشورهای پشتیبانی‌شده درج نشده است؛ OpenAI تصریح می‌کند دسترسی یا ارائه دسترسی از کشورهای خارج از فهرست ممکن است به مسدودشدن یا تعلیق حساب منجر شود. آلمان در فهرست قرار دارد، اما محل استقرار سرور یا محل حساب به‌تنهایی مجوز ارائه سرویس به کاربران کشورهای پشتیبانی‌نشده نیست.

نتیجه معماری:
- OpenAI Adapter فقط پس از تأیید انطباق کشور/کاربر/نحوه ارائه سرویس فعال می‌شود.
- برای مخاطبان داخل ایران، نباید دسترسی OpenAI را با VPN، واسطه یا پنهان‌سازی موقعیت دور زد.
- انتخاب Provider جایگزین نیز نیازمند بررسی رسمی کشورهای مجاز، شرایط استفاده، پرداخت، حریم خصوصی و دسترسی شبکه است.
- تا تعیین تکلیف، Provider در محیط production باید قابل غیرفعال‌سازی باشد و Public Assistant نباید برای منطقه/کاربر فاقد مجوز، درخواست AI ارسال کند.

مرجع رسمی: https://help.openai.com/en/articles/5347006-openai-api-supported-countries-and-territories

## 7. Rate limit و هزینه

تصمیم اولیه: Rate limit اتمیک و مشترک با PostgreSQL/Supabase برای MVP، پشت Port مستقل. کلید محدودسازی با HMAC از شناسه‌های لازم ساخته می‌شود؛ IP خام ذخیره نمی‌شود. این انتخاب هزینه سرویس خارجی را حذف می‌کند و برای حجم اولیه ساده‌تر است.

محدودیت: در ترافیک بالا، فشار نوشتن روی دیتابیس می‌تواند نامناسب شود. در آن حالت Adapter به Redis/سرویس تخصصی تغییر می‌کند، بدون تغییر Use Case.

الزامات:
- شمارش اتمیک در یک transaction/function.
- TTL و پاکسازی bucketهای منقضی.
- محدودیت هم‌زمانی و حداکثر هزینه.
- fail-closed برای مسیر عمومی در صورت ازکارافتادن limiter، با پاسخ موقتاً unavailable.
- کلید HMAC از secret سرور؛ نه hash ساده IP.
- IP فقط از proxy مورد اعتماد و پس از تعیین پلتفرم استخراج می‌شود.

## 8. Backup و بازیابی

- backup دیتابیس و فایل‌ها طبق سیاست مصوب.
- آزمون restore دوره‌ای.
- migration و backup قبل از تغییر schema.
- runbook برای افشای secret، اختلال Provider، خرابی DB و بازگشت نسخه.
- backup نباید retention حذف‌شده را بی‌نهایت زنده نگه دارد؛ سیاست چرخه عمر باید مشخص شود.

## 9. موارد باز و مسدودکننده production

- پلتفرم و منطقه میزبانی.
- مجازبودن Provider برای کشور محل استفاده و کشورهای کاربران هدف.
- مسیر دسترسی پایدار به OpenAI از محیط production.
- سقف بودجه و هشدار هزینه.
- شرایط حساب OpenAI و retention واقعی.
- محل و سیاست نگهداری داده.
- روش backup/restore و RPO/RTO.
- دامنه نهایی و originهای مجاز.
