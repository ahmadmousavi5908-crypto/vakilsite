# 26 — مشخصات طراحی پنل MAVIS و تجربه فشرده مقالات
تاریخ: 2026-11-08
وضعیت: طراحی محصول/UX؛ بدون تغییر CSS یا UI سایت در این مرحله.

## 1. هدف طراحی
ساخت فضای مدیریتی ممتاز، آرام، حرفه‌ای و کم‌اصطکاک که برای کار روزانه با صدها مقاله و چند مأموریت مستقل قابل استفاده باشد. طراحی نباید شبیه داشبورد عمومی SaaS یا پنل شلوغ و کارت‌محور شود.

## 2. خط قرمز بصری
- baseline سایت فعلی حفظ شود؛ هیچ selector عمومی، globals.css، Header، footer، menu، داک معرفی وکیل یا dock MAVIS فعلی در این فاز تغییر نمی‌کند.
- پنل MAVIS به‌صورت مسیر و stylesheet ماژولار و مستقل طراحی شود.
- پالت مرجع قابل استخراج از globals فعلی: navy #142b43، navy2 #24465a، gold #b9955d، gold-light #e5d1a7، cream #f5f4ee، paper #fcfbf8، ink #263746، muted #697987، line #e5e5dc، teal #236f6b، teal-deep #185b58، teal-soft #eaf3f1، sage #dcebe6.
- استفاده از طلایی برای تأکید و CTA محدود؛ سطح اصلی روشن و خوانا، سرمه‌ای برای ساختار و teal برای وضعیت‌های موفق/عملیاتی.
- سایه‌ها کم، خطوط ظریف، radius محدود و یکدست، فاصله‌گذاری دقیق و typography فارسی واضح.
- انیمیشن فقط برای بازخورد کوتاه و با reduced-motion؛ نه تزئین دائمی.
- در موبایل اولویت با دسترسی سریع، ارتفاع کم و کنترل‌های لمسی مناسب است.

## 3. ساختار ناوبری پیشنهادی
پنل فعلی سایت دست‌نخورده می‌ماند و MAVIS به‌صورت یک بخش مستقل و قابل شناسایی به منوی مدیریت افزوده می‌شود:
- نمای کلی MAVIS
- پذیرش هوشمند
- پژوهش و مدیریت مقالات
- رشد و تحلیل سایت
- تبلیغات Google Ads
- گزارش اجراها و تأییدها
- تنظیمات اتصال‌ها و منابع

نمایش آیتم‌ها بر اساس مجوز واقعی کاربر است؛ پنهان‌کردن منو جایگزین authorization سمت سرور نیست.

## 4. نمای کلی MAVIS
بالای صفحه: عنوان، توضیح کوتاه، وضعیت سرویس‌ها و زمان آخرین همگام‌سازی.
سه ماژول اصلی در سه ناحیه واضح:
1. پذیرش هوشمند: فرم‌های فعال، درخواست‌های در انتظار بررسی، خطاها و وضعیت handoff.
2. مرکز مقالات: موضوعات پژوهشی جدید، پیش‌نویس‌های metadata، مقالات منتظر بازبینی و انتشارهای اخیر.
3. رشد و جذب: شاخص‌های Search Console، Bing و Ads با تاریخ داده و نشانگر stale/connected/not connected.
بخش پایین: آخرین اجراها، نیازمند تأیید، خطاها و فعالیت قابل ممیزی.
هیچ شاخص یا اتصال فاقد منبع نباید با عدد صفر یا وضعیت سبز جعلی نمایش داده شود؛ وضعیت «متصل نیست/داده موجود نیست» صریح باشد.

## 5. مرکز مدیریت مقالات — جدول فشرده
### 5.1 ساختار ردیف بسته
ستون‌ها:
- کنترل باز/بسته (+ / −)
- شماره نمایشی
- شناسه پایدار مقاله
- عنوان مقاله
- دسته
- وضعیت تحریریه/حقوقی
- وضعیت انتشار/کشف‌پذیری
- تاریخ آخرین تغییر
- منوی عملیات مجاز

شناسه پایدار با ترتیب ردیف یا فیلتر تغییر نمی‌کند. شماره نمایشی می‌تواند با مرتب‌سازی تغییر کند و نباید به‌عنوان primary key استفاده شود.

### 5.2 ردیف بازشده
با کلیک +، جزئیات همان مقاله درجا زیر ردیف باز شود:
- خلاصه موضوع و نیت جست‌وجو
- کلیدواژه اصلی و فرعی
- slug و دسته
- ساختار H1/H2/H3 و FAQ پیشنهادی
- متا title/description
- لینک داخلی پیشنهادی
- منابع، URL، تاریخ بررسی و وضعیت اعتبار
- انطباق با قوانین ایران و موارد باز
- یادداشت بازبین و تاریخچه وضعیت
- وضعیت preview، approval، publish و indexing

در هر لحظه، بازشدن ردیف نباید باعث جابه‌جایی ناگهانی جدول یا از دست رفتن context کاربر شود. در صورت نیاز، حالت تک‌ردیفی یا چندردیفی پس از تست UX انتخاب شود.

### 5.3 کنترل‌های بالای جدول
- جست‌وجوی سریع در عنوان، شناسه، slug و کلیدواژه.
- فیلتر دسته، وضعیت حقوقی، وضعیت تحریریه، انتشار، منبع، بازه تاریخ و مسئول بازبینی.
- مرتب‌سازی بر اساس آخرین تغییر، عنوان، وضعیت و تاریخ انتشار.
- شمارنده نتایج فیلترشده و clear filters.
- انتخاب چندگانه فقط برای عملیات غیرمخرب و امن؛ انتشار گروهی یا حذف گروهی بدون approval جداگانه ممنوع.
- حفظ فیلتر/مرتب‌سازی در URL یا state قابل بازگشت، بدون ذخیره اطلاعات محرمانه در URL.

### 5.4 مقیاس‌پذیری ۳۰۰ تا ۴۰۰+ رکورد
- ابتدا query سمت سرور و indexهای PostgreSQL برای فیلترهای پرتکرار طراحی شوند.
- صفحه‌بندی اجباری نباشد؛ برای ۳۰۰ تا ۴۰۰ رکورد می‌توان با محدودیت query و رندر تدریجی/virtualization benchmark کرد.
- همه رکوردها یک‌باره به client ارسال نشوند اگر حجم metadata یا عملکرد این کار را ناموجه کند.
- search debounce کنترل‌شده و query قابل لغو باشد.
- مرتب‌سازی پایدار با tie-breaker شناسه انجام شود.
- حالت بدون نتیجه، loading، error و stale data طراحی شود.

### 5.5 دسترس‌پذیری و موبایل
- کنترل +/− دارای aria-expanded و aria-controls باشد؛ قابل استفاده با Enter/Space.
- عنوان و شناسه در همه عرض‌ها قابل مشاهده بمانند.
- در موبایل، هر ردیف به summary row فشرده تبدیل شود و جزئیات در پنل بازشونده زیر آن قرار گیرد؛ اسکرول افقی سراسری تحمیل نشود.
- وضعیت‌ها فقط با رنگ نشان داده نشوند؛ متن و آیکون هم داشته باشند.
- focus، کنتراست، اندازه لمس و prefers-reduced-motion رعایت شود.

## 6. فرم پژوهش و تکمیل metadata مقاله
- فرم موجود سایت/پنل ابتدا ممیزی شود؛ فرم موازی بدون ضرورت ساخته نشود.
- ورودی‌های فرم به گروه‌های «موضوع و هدف»، «SEO و ساختار»، «منابع حقوقی»، «بازبینی و انتشار» تقسیم شوند.
- اطلاعات کشف‌شده توسط سیستم با برچسب «پیشنهاد خودکار/نیازمند تأیید» از اطلاعات تأییدشده جدا باشد.
- هر URL منبع دارای publisher، نوع منبع، تاریخ مشاهده، وضعیت دسترسی و اعتبارسنجی باشد.
- فیلدهای متن و metadata قابل کپی یک‌جا و جداگانه باشند.
- تولید متن مقاله توسط MAVIS ممنوع باقی می‌ماند.
- پیش‌نمایش مقاله از محتوای واقعی سایت استفاده کند و پس از approval هیچ تغییر پنهانی در متن اعمال نشود.

## 7. فرم پذیرش هوشمند
- طراحی مرحله‌ای و شرطی؛ تمام پرسش‌های لازم حفظ شوند.
- فشرده‌سازی از طریق grouping، grid دو ستونه برای گزینه‌های کوتاه، disclosure کنترل‌شده و نمایش پرسش‌های وابسته انجام شود.
- کاربر همیشه بداند در کدام مرحله است، چرا پرسش مطرح شده و کدام فیلد اختیاری است.
- انتخاب موضوع دستی همیشه در دسترس باشد؛ تشخیص محدود موضوع صرفاً پیشنهاد مسیر است.
- گزارش نهایی فقط از پاسخ‌های صریح کاربر تشکیل شود؛ متن آزاد کاربر بدون تفسیر یا تغییر معنا نقل/خلاصه وفادار شود.
- چک‌لیست مدارک به‌عنوان «مدارک احتمالی برای آماده‌سازی» نمایش داده شود، نه اعلام کفایت قانونی.
- امکان بازبینی گزارش توسط کاربر پیش از ارسال؛ هیچ ارسال خودکاری رخ ندهد.
- راهنمایی ایمنی عمومی و فوریت باید از تحلیل حقوقی پرونده جدا باشد.

## 8. صفحه رشد و Google Ads
- شاخص‌ها همراه با تاریخ بازه، منبع داده، timezone و تازگی داده نشان داده شوند.
- Search Console: clicks, impressions, CTR, average position با هشدار درباره محدودیت داده API.
- Ads: spend, impressions, clicks, conversions و cost/conv با تعریف conversion و attribution window روشن.
- مقایسه Ads و organic تنها با بازه، timezone و تعریف شاخص یکسان.
- عبارت «موکل جذب‌شده» فقط با رویداد تبدیل معتبر و کنترل کیفیت سرنخ استفاده شود.
- کمپین‌ها در فاز اول read-only؛ تغییرات تنها در preview و تأیید جداگانه.

## 9. وضعیت‌های مشترک طراحی
- Not connected
- Connected / Read-only
- Syncing
- Data stale
- Needs review
- Approved
- Published
- Submission accepted
- Index observed
- Error
- Disabled

این وضعیت‌ها باید از state واقعی سرویس تغذیه شوند؛ رنگ یا animation جای داده واقعی را نمی‌گیرد.

## 10. معیار پذیرش طراحی
- سایت عمومی و ظاهر مصوب آن هیچ تغییری نکند.
- صفحه پنل در موبایل و دسکتاپ بدون overflow ناخواسته باشد.
- فهرست ۴۰۰ مقاله با داده آزمایشی قابل جست‌وجو، فیلتر و مرتب‌سازی باشد.
- باز/بسته کردن جزئیات درجا و با صفحه‌کلید کار کند.
- زمان پاسخ جست‌وجو و رندر با داده حجیم اندازه‌گیری و ثبت شود.
- همه وضعیت‌های loading/empty/error/stale/permission طراحی شده باشند.
- هیچ شاخص ساختگی، متن مقاله تولیدشده یا انتشار بدون تأیید وجود نداشته باشد.
- screenshotهای before/after از پنل و صفحات عمومی برای رگرسیون ثبت شوند؛ فقط پس از آن UI برای پذیرش ارائه شود.
