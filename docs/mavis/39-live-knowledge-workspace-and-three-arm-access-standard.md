# استاندارد دانش زنده MAVIS، تحویل بدون آرشیو و دسترسی یکپارچه سه بازو
نسخه 1.0 | 2026-11-08
وضعیت: استاندارد معماری پیشنهادی؛ اتصال اجرایی هنوز نیازمند تأیید Mother Two و آزمون runtime است.

## 1. تصمیم غیرقابل‌ابهام
MAVIS نباید برای استفاده از دانش روزمره، آرشیو فشرده بکاپ را باز کند یا به فایل ZIP/TAR به‌عنوان پایگاه دانش متکی باشد.

سه مفهوم از هم جدا هستند:
1. **Backup vault:** نسخه پشتیبان تغییرناپذیر برای بازیابی فاجعه؛ دسترسی عادی runtime ممنوع.
2. **Knowledge workspace:** فایل‌های مستقل، استخراج‌شده، قابل خواندن و قابل جست‌وجو در محیط کاری امن؛ مناسب بررسی، اصلاح و ingestion.
3. **Knowledge registry/runtime:** فهرست مرجع و داده‌های ساختاریافته‌ای که ماویس واقعاً از آن‌ها بازیابی می‌کند؛ منبع runtime باید قابل query باشد، نه اینکه هر بار پوشه‌ای از فایل‌ها را بخواند.

هیچ فایل فشرده‌ای به‌تنهایی «دانش قابل استفاده ماویس» محسوب نمی‌شود. هر منبع باید مسیر ورود، اعتبارسنجی، مالک، مجوز، نسخه، تاریخ اعتبار و وضعیت انتشار به registry داشته باشد.

## 2. شکل تحویل و دانلود
- بسته مستندات/دانش برای استفاده روزمره به‌صورت **فایل‌های مستقل** در مسیر workspace تحویل شود؛ از ساختن یک ZIP به‌عنوان خروجی نهایی خودداری شود.
- ساختار پوشه‌ها بر اساس دامنه و نوع منبع باشد، نه بر اساس تاریخ دانلود یا نام آرشیو:
  - `knowledge/legal/statutes/`
  - `knowledge/legal/unifying-opinions/`
  - `knowledge/legal/judicial-decisions/`
  - `knowledge/legal/advisory-opinions/`
  - `knowledge/legal/official-guidance/`
  - `knowledge/research/`
  - `knowledge/taxonomy/`
  - `knowledge/operations/`
  - `manifests/`
  - `reports/validation/`
- فرمت‌های مرجع: Markdown برای متن ساختاریافته و توضیحات، JSON برای metadata و قراردادها، JSONL برای رکوردهای مستقل و قابل پردازش، CSV فقط برای داده‌های جدولی ساده. PDF اصلی می‌تواند به‌عنوان سند منبع نگهداری شود، اما متن استخراج‌شده و metadata باید جداگانه و با پیوند به اصل سند ذخیره شوند.
- از فرمت‌های proprietary و فایل‌های غیرقابل‌خواندن به‌عنوان تنها نسخه داده اجتناب شود.
- دانلودها باید به مسیر staging نسخه‌دار بروند؛ فایل موجود بدون مقایسه hash هرگز overwrite نشود.
- دریافت باید resumable، idempotent و قابل retry باشد. هر فایل با SHA-256، اندازه، نوع محتوا، encoding و منبع ثبت شود.
- در صورت mismatch، فایل quarantine شود؛ نه اینکه وارد دانش فعال شود.
- هیچ داده محرمانه یا آرشیو Mother Two در GitHub، بسته عمومی یا مسیر قابل دسترس وب قرار نگیرد.

## 3. مسیر ورود تا استفاده واقعی
`Discover → Fetch → Verify → Parse → Normalize → Review → Register → Index → Query → Monitor`

1. Discover: منبع و هدف استفاده مشخص شود.
2. Fetch: فایل/داده از منبع مجاز دریافت شود.
3. Verify: hash، نوع فایل، حجم، encoding و سلامت محتوا کنترل شود.
4. Parse: متن/metadata استخراج شود؛ اصل سند دست‌نخورده بماند.
5. Normalize: رکورد استاندارد با شناسه پایدار ساخته شود.
6. Review: اعتبار منبع، کیفیت استخراج، تاریخ و وضعیت حقوقی بازبینی شود.
7. Register: شناسه و metadata در Knowledge Registry ثبت شود.
8. Index: متن و metadata در موتور جست‌وجوی مجاز ایندکس شود.
9. Query: هر بازو از API/سرویس دسترسی مجاز، نه از پوشه تصادفی، جست‌وجو کند.
10. Monitor: خطا، stale source، نسخه، زمان sync و سلامت index پایش شود.

تا پیش از عبور از Review و Register، محتوا در وضعیت `staged` است و نباید مبنای پاسخ حقوقی یا توصیه عملیاتی قرار گیرد.

## 4. قرارداد حداقلی هر رکورد دانش
هر رکورد باید حداقل این metadata را داشته باشد:
- `record_id`: شناسه پایدار و غیرقابل‌تغییر
- `source_id`: شناسه منبع
- `title`, `document_type`, `jurisdiction`
- `issuer` یا مرجع صادرکننده
- `official_url` و `retrieved_at`
- `published_at`, `effective_from`, `effective_to` در صورت وجود
- `legal_status`: current / amended / repealed / superseded / disputed / unknown
- `authority_level` با طبقه‌بندی متناسب با نوع سند
- `content_hash`, `parser_version`, `schema_version`
- `access_class`: public / internal / confidential
- `review_status`: staged / needs_review / approved / rejected
- `reviewed_by`, `reviewed_at`, `change_reason`
- `canonical_record_id` برای نسخه‌ها و اسناد مرتبط

فیلدهای نامعلوم باید null/unknown بمانند؛ حدس‌زدن تاریخ، اعتبار، مرجع یا شماره ماده ممنوع است.

## 5. مرجع واحد و جلوگیری از چند پایگاه دانش
- legal-library فعلی و هر central knowledge registry واقعی ابتدا inventory و تطبیق داده شوند.
- هیچ dataset موازی یا کپی مستقل از دانش حقوقی ساخته نشود.
- هر مفهوم فقط یک canonical record داشته باشد؛ نسخه‌ها، خلاصه‌ها، کلیدواژه‌ها و فایل اصلی با relation به آن وصل شوند.
- فایل‌های استخراج‌شده مشتق‌شده‌اند و باید به source artifact و hash اصل سند اشاره کنند.
- اگر داده‌ای در چند محل وجود دارد، ابتدا deduplicate و provenance بررسی شود؛ merge خودکار بدون گزارش و تأیید ممنوع.
- PostgreSQL/registry مرجع metadata و وضعیت باشد؛ full-text search روی متن مجاز انجام شود. vector index فقط در صورت اثبات بهبود کیفیت retrieval و هزینه/latency اضافه شود.
- Storage برای اصل اسناد حجیم و مشتقات مجاز است؛ دسترسی با مجوز و لینک امضاشده کوتاه‌عمر. فایل‌ها در دیتابیس به‌صورت blob حجیم کپی نشوند مگر توجیه فنی مستند داشته باشد.

## 6. دسترسی سه بازو از یک مرجع با سیاست جدا

| بازو | دانش مجاز | خروجی مجاز | ممنوع |
|---|---|---|---|
| Public Intake | taxonomy عمومی، تعریف ساده موضوعات، متن‌های تأییدشده راهنمای فرم | دسته‌بندی اولیه، پرسش بعدی، خلاصه پاسخ‌های کاربر | پرونده‌های داخلی، استدلال حقوقی شخصی‌سازی‌شده، پیش‌بینی نتیجه |
| Lawyer Copilot | منابع حقوقی تأییدشده و عمومی؛ داده داخلی فقط پس از سیاست مستقل و مجوز صریح | پژوهش با استناد، تعارض منابع، هشدار اعتبار و عدم قطعیت | استفاده از منبع تأییدنشده به‌عنوان قانون معتبر؛ افشای داده خارج از مجوز |
| Growth Intelligence | داده عمومی سایت، analytics و Search Console/Bing/Ads با مجوز و حداقل‌سازی | فرصت، تحلیل، گزارش و پیشنهاد | دسترسی به پرونده موکل، مکالمات محرمانه، تغییر کمپین/انتشار خودکار |

تمام بازوها از یک registry استفاده می‌کنند، اما retrieval gateway باید در هر query این موارد را enforce کند: identity، role، purpose، access_class، tenant، retention و allowed source types. فیلتر صرفاً در prompt کافی نیست؛ باید قبل از بازیابی و در سطح داده اعمال شود.

## 7. سه سطح آماده‌بودن دانش
- **L0 – Downloaded:** فایل دریافت شده و hash آن معتبر است.
- **L1 – Parsed & registered:** متن استخراج شده، metadata کامل و رکورد در registry ثبت شده است.
- **L2 – Approved & searchable:** بازبینی شده، وضعیت حقوقی/منبع روشن است، index فعال و retrieval test پاس شده است.

فقط L2 مجاز است در پاسخ حقوقی قطعی یا محتوای قابل اتکا استفاده شود. L0/L1 فقط برای پردازش و بازبینی داخلی‌اند.

## 8. رابط ساده مدیریت دانش در پنل
یک صفحه «مرکز دانش MAVIS» در پنل فعلی، بدون تغییر ظاهر سایت عمومی:
- کارت‌های وضعیت: دریافت‌شده، در انتظار بررسی، تأییدشده، نیازمند به‌روزرسانی، خطادار.
- دکمه‌های واضح: «دریافت منابع»، «بررسی فایل‌ها»، «تطبیق موارد تکراری»، «ارسال برای بازبینی»، «تأیید و فعال‌سازی»، «بازسازی نمایه».
- هر ردیف: عنوان، نوع منبع، مرجع، تاریخ اعتبار، نسخه، سطح دسترسی، وضعیت، آخرین sync و تعداد استفاده.
- پنل جزئیات: اصل منبع، متن استخراج‌شده، metadata، hash، سابقه تغییر، روابط و خطاهای parser.
- جست‌وجو، فیلتر، مرتب‌سازی و عملیات گروهی با preview و شمارش؛ حذف/جایگزینی گروهی نیازمند تأیید دوم.
- کار طولانی با job ID، درصد/مرحله، زمان آخرین پیشرفت، retry و لغو امن نمایش داده شود.
- دسترسی‌ها: owner_admin تأیید/فعال‌سازی؛ researcher آماده‌سازی؛ lawyer بازبینی حقوقی؛ analyst فقط گزارش؛ public هیچ دسترسی به مرکز دانش ندارد.
- رابط باید فارسی، RTL، واکنش‌گرا، قابل‌استفاده با صفحه‌کلید و دارای پیام خطای روشن باشد.

## 9. کارایی و استفاده آسان برای مدل
- MAVIS در زمان پاسخ فقط از Retrieval Gateway نسخه‌دار استفاده کند؛ هر درخواست archive scan یا directory crawl ممنوع.
- ابتدا metadata filter و PostgreSQL full-text؛ سپس rerank فقط در صورت نیاز و با سقف latency.
- متن chunkها با حفظ ماده/بند/صفحه و عنوان منبع قطعه‌بندی شود؛ citation به صفحه/ماده/بند واقعی برگردد.
- هر پاسخ Copilot باید source IDs و content hashes مصرف‌شده را ثبت کند تا بازتولیدپذیر باشد.
- cache فقط برای محتوای عمومی و غیرحساس یا با کلیدهای دقیق مجوزمند؛ cache مشترک بین کاربران/نقش‌ها ممنوع.
- retrieval budget: سقف تعداد اسناد و حجم متن، timeout، سقف هزینه و fallback روشن.
- اگر index خراب یا stale باشد، سیستم نباید به‌جای آن silently از تمام پوشه‌ها بخواند؛ وضعیت unavailable/partial و راه اصلاح نمایش داده شود.
- تغییر یک سند فقط همان record/chunks/index را invalidate کند، نه کل دانش را.
- sync افزایشی بر اساس hash و timestamp؛ پردازش تکراری فایل بدون تغییر ممنوع.

## 10. معیار پذیرش فنی و عملیاتی
تحویل دانش تنها وقتی کامل است که همه موارد زیر شواهد داشته باشند:
1. فایل‌های مستقل در مسیر workspace وجود داشته باشند و archive لازم نباشد.
2. تمام فایل‌ها hash، اندازه، نوع و منبع ثبت‌شده داشته باشند.
3. استخراج متن و metadata با نمونه‌گیری انسانی تأیید شده باشد.
4. رکوردهای تکراری/متعارض گزارش شده باشند و merge بی‌اجازه رخ نداده باشد.
5. رکوردهای تأییدشده در registry و index قابل query باشند.
6. سه بازو با نقش‌های مجاز retrieval test جداگانه پاس کنند.
7. آزمون منفی ثابت کند Intake و Growth به داده حقوقی محرمانه دسترسی ندارند.
8. Copilot citation را به منبع و بخش دقیق برگرداند.
9. به‌روزرسانی یک منبع، نسخه قبلی و تاریخچه را حفظ کند.
10. restore backup به workspace/index عملیاتی با دستورالعمل آزموده‌شده ممکن باشد.
11. زمان p50/p95، نرخ خطا و هزینه retrieval ثبت شود.
12. UI مدیر بتواند بدون دست‌کاری فایل یا اجرای دستور shell وضعیت را مدیریت کند.

## 11. سیاست بکاپ
- بکاپ مادر دو immutable و خارج از runtime باقی می‌ماند.
- از registry، manifestها، metadata، تنظیمات و Storage objects سیاست backup جداگانه لازم است؛ backup دیتابیس لزوماً فایل‌های Storage را پوشش نمی‌دهد.
- restore ابتدا به محیط ایزوله انجام شود؛ hash و تعداد رکوردها تطبیق یابد؛ سپس با تأیید مالک به staging/runtime منتقل شود.
- هیچ‌گاه archive کامل مستقیماً روی workspace یا production extract نشود.
- نسخه فعال knowledge snapshot باید قابل rollback باشد؛ تغییر registry/index با migration یا release version ثبت شود.

## 12. مسیر اجرا و توقف‌های ایمن
1. دریافت خروجی Termux و بررسی صحت Mother Two، inventory و source paths.
2. ساخت گزارش اختلاف میان archive، workspace، Git branches و registry موجود؛ بدون کپی یا حذف.
3. تعیین canonical source برای هر dataset و رفع ابهام مالکیت/نسخه.
4. طراحی mapping از ساختار واقعی موجود به قرارداد این سند؛ عدم ساخت dataset موازی.
5. پیاده‌سازی parser/manifest و workspace materialization در staging.
6. اتصال read-only به registry و اجرای retrieval tests.
7. افزودن مرکز دانش به پنل مدیریت، پس از تأیید baseline UI.
8. فعال‌سازی تدریجی هر بازو پس از مجوز، تست منفی، benchmark و تأیید مالک.

اگر baseline واقعی با ممیزی قبلی فرق داشت، توقف و بازطراحی؛ نه تلاش برای جا دادن Mother Two در فرض‌های قبلی.

## 13. وضعیت صادقانه
این سند استاندارد و طرح رفع ضعف آرشیو-محوری است. تا زمانی که Mother Two واقعی بررسی نشده و ingestion، registry، index، Retrieval Gateway و UI در runtime تست نشده‌اند، هیچ‌یک را «پیاده‌سازی‌شده» یا «قابل‌استفاده توسط MAVIS» اعلام نکنید.
