# سیاست تجمیع دانش تاریخی و کتابخانه‌های قبلی MAVIS
نسخه 1.0 | 2026-11-08
وضعیت: استاندارد ممیزی و ادغام؛ موجودی نهایی باید از محیط محلی و شاخه‌ها دوباره استخراج شود.

## 1. الزام محصول
MAVIS باید از دانش جدید و نیز دانش تاریخی Vakilsite/MAVIS استفاده کند. دانش قدیمی صرفاً به‌دلیل قدیمی‌بودن کنار گذاشته نمی‌شود؛ اما بدون بررسی منشأ، نسخه، اعتبار حقوقی، مجوز و تکراری‌بودن نیز وارد پاسخ فعال نمی‌شود.
هدف، یکپارچه‌سازی منابع موجود است، نه بازسازی آن‌ها و نه ساخت کتابخانه موازی.

## 2. شواهد تاریخی که باید حفظ شوند
گزارش‌های قبلی پروژه موارد زیر را ثبت کرده‌اند:
- در 2026-11-06 انتقال 32 فایل Markdown گزارش شده: 9 فایل SEO و 23 فایل MAVIS؛ بدون overwrite، conflict یا حذف. docs/search-discovery.md نیز حفظ شده است.
- آرشیوهای قدیمی گزارش‌شده شامل vakilsite-mother-two-20261105-141949-full.tar.gz و نسخه github-safe هستند.
- بسته‌های اسناد MAVIS گزارش‌شده شامل mavis-docs-verified-20261104-023756.tar.gz و mavis-forensic-20261104-024718.tar.gz هستند.
- گزارش‌های قبلی به 32 سند پژوهشی، 11 dataset و 47 مسیر مرجع اشاره کرده‌اند؛ این شمارش‌ها باید با فایل‌های واقعی، manifest و hash تطبیق داده شوند و تا آن زمان inventory قطعی نیست.
- مسیرهای docs/knowledge/README.md و docs/knowledge/manifest.json در گزارش‌های قبلی نام برده شده‌اند؛ وجود و محتوای آن‌ها باید در workspace، آرشیوها و Git refs بررسی شود، نه اینکه وجود فعلی‌شان مفروض گرفته شود.
- یک snapshot به نام VAKILSITE-MOTHER-TWO-PLUS-KNOWLEDGE-20261106-193055 با 135 فایل گزارش شده، اما کامل‌بودن تاریخی آن تأیید نشده است.
- بکاپ Mother Two به‌روزشده 2026-11-06 با SHA-256 ثبت‌شده توسط مالک، نسخه مرجع حفاظتی است و باید immutable بماند. گزارش صحت آرشیو و مقایسه منابع، جایگزین inventory محتوای علمی/حقوقی نیست.
این موارد سرنخ‌های دارای سابقه هستند؛ شمارش و حضور فایل‌ها باید در اجرای محلی دوباره ثابت شود.

## 3. منابع تاریخی قابل بررسی
ممیزی باید این سطوح را پوشش دهد:
1. workspace فعال و فایل‌های واقعی Mother Two؛
2. بکاپ‌های قدیمی Mother Two و نسخه GitHub-safe؛
3. بسته‌های مستندات MAVIS و forensic؛
4. تمام شاخه‌ها، tagها و commitهای GitHub مرتبط؛
5. src/data, src/app, src/components, docs و هر legal-library موجود؛
6. manifestها، registryها، فایل‌های taxonomy، JSON/JSONL/CSV، Markdown، PDF و داده‌های استخراج‌شده؛
7. داده‌های Supabase/Storage فقط با دسترسی مجاز و پس از شناسایی schema و سیاست محرمانگی؛
8. خروجی‌های پژوهشی، source maps، گزارش‌های سرچ/SEO و تصمیم‌های معماری قبلی.
هر منبع باید به مسیر/commit/archive دقیق و hash قابل بازتولید ارجاع داشته باشد. از اسم فایل به‌تنهایی وجود محتوا نتیجه‌گیری نشود.

## 4. روش تطبیق بدون از دست‌دادن تاریخچه
- فقط خواندن در مرحله discovery؛ هیچ pull، merge، reset، stash، checkout، overwrite یا حذف انجام نشود.
- برای هر فایل یک inventory row بسازید: path، source container، Git ref/archive، byte size، SHA-256، Git blob SHA در صورت وجود، format، encoding، category، access class و extraction status.
- فایل‌های byte-identical با SHA-256 گروه‌بندی شوند؛ فقط یک canonical payload نگهداری شود و همه provenanceها حفظ شوند.
- فایل‌های هم‌نام با hash متفاوت conflict هستند، نه duplicate. هر دو نسخه نگهداری و diff/lineage گزارش شود.
- نسخه‌های اصلاح‌شده، ترجمه‌ها، خلاصه‌ها و مشتقات نباید به‌اشتباه حذف شوند؛ رابطه derived_from و supersedes ثبت شود.
- محتواهای مشابه ولی متفاوت با fingerprint متنی/عنوان/منبع علامت‌گذاری شوند؛ ادغام خودکار ممنوع.
- اسناد پژوهشی قدیمی به‌صورت خودکار قانون جاری تلقی نشوند؛ در موضوع حقوق ایران، اعتبار زمانی و منبع رسمی باید دوباره بررسی شود.
- محتوای غیرحقوقی (SEO، UX، محصول، معماری) در دامنه خودش حفظ و به Legal Copilot تزریق نشود مگر ارتباط مستند داشته باشد.

## 5. رجیستری واحد و شناسه‌های پایدار
- ابتدا registry واقعی موجود کشف شود؛ registry جدید ایجاد نشود مگر پس از اثبات نبود نمونه موجود و تصویب مالک.
- رکورد canonical دارای record_id پایدار باشد؛ تمام نسخه‌ها، فایل‌های اصلی، استخراج‌ها و خلاصه‌ها به آن متصل شوند.
- source_id, source_path, source_revision, sha256, retrieved_at, published_at, valid_from, valid_to, jurisdiction, authority, legal_status, access_class, review_status, parser_version و derived_from ثبت شوند.
- manifest فقط فهرست فایل نیست؛ باید مسیر فایل مستقل، hash، نسخه schema، وضعیت parse/review/index و ارتباط آن با canonical record را مشخص کند.
- registry باید قابلیت reverse lookup داشته باشد: هر پاسخ MAVIS به record و منبع اصلی بازگردد.

## 6. اتصال سه بازو به تاریخچه
- Public Intake: taxonomyها، پرسش‌نامه‌ها، الگوهای پذیرش و متن‌های عمومی تأییدشده قدیمی را بازیابی کند؛ نسخه‌های قدیمی فرم قبل از جایگزینی قابل مقایسه باشند.
- Lawyer Copilot: legal-library، قوانین، آرا، نظریات و پژوهش‌های قبلی را با ارزیابی دوباره اعتبار و تاریخ استفاده کند؛ خلاصه ثانویه هرگز جای اصل منبع را نگیرد.
- Growth Intelligence: اسناد SEO، تحقیق مخاطب، تحلیل شهرها، تصمیم‌های قبلی، metadata و نتایج Search Console/Bing موجود را با تاریخ و منبع نگهداری کند؛ داده قدیمی را به‌عنوان عملکرد فعلی نمایش ندهد.
- هسته مشترک: provenance و مجوز را enforce کند؛ یک بازو نمی‌تواند به دلیل دسترسی بازوی دیگر داده‌ای را ببیند.

## 7. خروجی قابل استفاده، نه آرشیو جدید
نتیجه ممیزی باید در workspace مستقل به فایل‌های قابل خواندن تبدیل شود:
- inventory.csv و inventory.jsonl
- duplicate-groups.json
- conflicts.json
- source-lineage.jsonl
- missing-or-unreadable.csv
- registry-mapping.md
- ingestion-plan.md
- validation-report.md
- فایل‌های canonical مستقل در مسیرهای دسته‌بندی‌شده.
این‌ها گزارش و فایل‌های داده‌ای مستقل‌اند؛ نه یک TAR/ZIP که کاربر بعداً نتواند از آن استفاده کند. آرشیوهای اصلی فقط immutable backup باقی می‌مانند.

## 8. معیارهای پذیرش تاریخی
1. تمام 32 فایل انتقال‌یافته قبلی با hash و مسیر فعلی تطبیق داده شوند.
2. 9 سند SEO و 23 سند MAVIS در inventory قابل مشاهده و قابل جست‌وجو باشند.
3. شمارش‌های 32 research docs، 11 datasets و 47 references به‌صورت فایل‌به‌فایل تأیید یا اصلاح شوند.
4. گزارش مشخص کند کدام محتوا فقط در archive، کدام در workspace، کدام در Git refs و کدام در registry وجود دارد.
5. تفاوت Mother Two محلی با tag/branch GitHub آشکارا گزارش شود؛ هیچ‌کدام جانشین دیگری فرض نشود.
6. هر duplicate، conflict، missing file و parse failure فهرست داشته باشد.
7. داده‌های تاریخی در workspace مستقل و قابل استفاده باقی بمانند.
8. حداقل یک retrieval test برای نمونه‌ای از هر طبقه دانش و هر سه بازو انجام شود.
9. تست مجوز منفی ثابت کند داده محرمانه یا غیرمرتبط از بازوها عبور نمی‌کند.
10. گزارش سرعت p50/p95 و نرخ خطا بعد از indexing ثبت شود.

## 9. توقف‌های ایمن
- Mother Two original و بکاپ‌های تاریخی overwrite یا extract-in-place نشوند.
- اگر آرشیو رمزگذاری نشده و حاوی اطلاعات حساس است، دسترسی workspace با مجوز فایل محدود شود و هیچ‌گاه به GitHub عمومی/شاخه docs منتقل نشود.
- اگر source lineage نامعلوم است، رکورد quarantine شود.
- اگر registryهای متعارض یافت شدند، ادغام متوقف و تصمیم مالک ثبت شود.
- هیچ فایل یا رکوردی فقط به‌دلیل قدیمی بودن حذف نشود.
- هیچ ادعای کامل‌بودن inventory پیش از بررسی محلی و ارائه manifest/hash پذیرفته نیست.

## 10. وضعیت صداقت
این سند سیاست استفاده از دانش تاریخی را مشخص می‌کند. به‌روزرسانی registry، استخراج مجدد، indexing و اتصال runtime هنوز باید با اجرای ممیزی read-only در Termux و سپس پیاده‌سازی کنترل‌شده انجام شود. مستندات GitHub جایگزین داده واقعی پروژه نیست.
