# 21 — برنامه اتصال دانش MAVIS و ارتقای بکاپ مادر دو

**وضعیت:** ثبت در برنامه؛ اجرا و تأیید مرحله‌ای لازم است  
**تاریخ ثبت:** 2026-11-06  
**دامنه:** اسناد، دانش حقوقی، بازیابی MAVIS و حفاظت از وضعیت تأییدشده Vakilsite  
**اصل حاکم:** این سند مجوز تغییر UI، کد اجرایی، دیتابیس، انتشار یا ادغام شاخه‌ها نیست.

## 1. گام بعدی اصلی: اتصال دانش به MAVIS

### هدف
استفاده واقعی و کنترل‌شده از دانش موجود در پروژه، بدون ساخت کتابخانه موازی و بدون انتشار ناخواسته اسناد داخلی.

### وضعیت مبنا
- فهرست مرکزی دانش در محیط محلی پروژه ساخته و اعتبارسنجی شده است: ۳۲ سند پژوهشی، ۱۱ مجموعه داده موجود، ۴ سطح/مسیر runtime و ۴۷ ارجاع تأییدشده.
- فایل‌های محلی ثبت‌شده: `docs/knowledge/README.md` و `docs/knowledge/manifest.json`.
- این دو فایل در زمان ثبت این سند هنوز در شاخه GitHub فعلی مشاهده نشده‌اند؛ انتقال آن‌ها به شاخه باید پس از مقایسه وضعیت محلی و remote انجام شود.
- زیرساخت حقوقی موجود شامل `src/data/legal-library/` و `src/lib/legal-library.js` است و باید مبنای اتصال باقی بماند.
- آماده‌سازی فهرست دانش به معنی پیاده‌سازی retrieval یا فعال‌شدن قابلیت در MAVIS نیست.

### دو مسیر بررسی‌شده
1. **MVP با جست‌وجوی قطعی روی داده‌های موجود:** جست‌وجوی فارسی/کلیدواژه‌ای روی JSONهای حقوقی و metadata فهرست مرکزی، با کنترل دسترسی، تاریخ اعتبار و استناد.
2. **جست‌وجوی معنایی با embedding و vector database:** قابلیت بالقوه بهتر برای پرسش‌های پیچیده، اما با هزینه، زیرساخت و سطح عملیاتی بیشتر.

**مسیر منتخب برای مرحله اول:** مسیر ۱؛ چون داده ساختاریافته و runtime موجود است، منابع و مجوزها هنوز نیازمند ممیزی‌اند و افزودن زیرساخت جدید فعلاً توجیه اثبات‌شده ندارد. مسیر ۲ فقط پس از سنجش کیفیت retrieval و حجم واقعی داده دوباره ارزیابی می‌شود.

### چک‌لیست اجرایی
- [ ] مقایسه وضعیت محلی و remote و ثبت دقیق commit/working tree؛ بدون reset، clean، checkout اجباری یا force push.
- [ ] انتقال کنترل‌شده `docs/knowledge/README.md` و `docs/knowledge/manifest.json` به شاخه کاری مورد تأیید، بدون overwrite.
- [ ] بازبینی مسیرهای manifest و تطبیق آن‌ها با فایل‌های واقعی پروژه.
- [ ] ممیزی runtime واقعی MAVIS، مسیرهای API، مرزهای Public/Private، احراز هویت و مجوزها.
- [ ] تعیین مجموعه داده‌های قابل retrieval و حذف کامل اسناد داخلی MAVIS/SEO از پاسخ عمومی.
- [ ] طراحی قرارداد Retrieval Port و خروجی دارای source ID، نسخه منبع، تاریخ اعتبار و وضعیت تأیید.
- [ ] طراحی فیلترهای مجوز، freshness، نسخه‌بندی قوانین، اصلاح/نسخ و جلوگیری از citation ساختگی.
- [ ] ساخت نمونه اولیه فقط‌خواندنی و deterministic روی کتابخانه موجود؛ بدون اتصال Provider و بدون تغییر UI.
- [ ] ساخت تست برای پرسش‌های فارسی، مترادف‌ها، نبود منبع، منبع منقضی، منبع متعارض و تلاش prompt injection.
- [ ] ارائه گزارش کیفیت و طرح نهایی برای تأیید مالک، پیش از هر تغییر runtime.
- [ ] پس از تأیید جداگانه، پیاده‌سازی محدود در شاخه مستقل و اجرای تست‌های واقعی.

### معیار پایان
MAVIS بتواند فقط از منابع مجاز و قابل ردیابی بازیابی کند؛ هر نتیجه به منبع و نسخه آن متصل باشد؛ اسناد داخلی به کاربر عمومی نشت نکند؛ و در نبود منبع معتبر، پاسخ قطعی تولید نشود. تا تحقق و تست این معیارها، retrieval «پیاده‌سازی‌شده» محسوب نمی‌شود.

## 2. ارتقای بکاپ مادر دو

### اصل حفاظت
- بکاپ اصلی `VAKILSITE-MOTHER-TWO-20261105` یک baseline تاریخی و دست‌نخورده است؛ هرگز overwrite، rename یا حذف نشود.
- نسخه جدید باید با شناسه مستقل، تاریخ، ساعت و پسوند روشن ساخته شود؛ پیشنهاد شناسه: `VAKILSITE-MOTHER-TWO-PLUS-KNOWLEDGE-20261106`.
- بکاپ جدید باید از workspace واقعی و تأییدشده Termux تهیه شود تا تغییرات محلی و فایل‌های untracked نیز جا نمانند.
- GitHub checkpoint به‌تنهایی جایگزین آرشیو محلی کامل نیست؛ این دو باید جداگانه ثبت شوند.

### دو مسیر
1. **ساخت آرشیو از workspace فعلی:** تغییرات tracked و untracked را در یک snapshot واحد نگه می‌دارد و بهترین مبنا برای ادامه کار است.
2. **ساخت آرشیو صرفاً از Git commit:** تمیزتر است، اما تغییرات محلی ثبت‌نشده را حذف می‌کند و برای وضعیت فعلی قابل قبول نیست.

**مسیر منتخب:** آرشیو workspace فعلی، پس از preflight و فهرست‌برداری؛ چون هدف حفظ تمام داده‌های افزوده‌شده و تغییرات محلی است.

### محتوای الزامی بسته پشتیبان
- snapshot کامل فایل‌های پروژه، شامل کد، محتوا، docs/seo، docs/mavis، docs/knowledge، فایل‌های پژوهشی و فایل‌های rollback موجود.
- فهرست مسیرها، نوع فایل، اندازه و SHA-256 برای هر فایل.
- شناسه بکاپ، تاریخ و timezone، مسیر منبع، Git HEAD، وضعیت branch و خلاصه Git status.
- فهرست فایل‌های حساس یا حجیم مستثناشده؛ هیچ secret، token، کلید API یا داده محرمانه موکل وارد آرشیو قابل اشتراک نشود.
- راهنمای فارسی بازیابی با مسیر مقصد، ترتیب استخراج، نصب وابستگی‌ها و هشدارهای لازم.
- فایل checksum کل آرشیو و manifest مستقل.

### روش تأیید
- [ ] تأیید وجود و سلامت بکاپ مادر دو اصلی؛ فقط خواندن، بدون تغییر.
- [ ] بررسی فضای آزاد و فهرست کامل workspace.
- [ ] ثبت HEAD، وضعیت Git و همه فایل‌های untracked/modified.
- [ ] تعیین صریح exclusions؛ حذف فایل‌ها فقط با ثبت در manifest، نه حذف از workspace.
- [ ] ساخت آرشیو جدید خارج از پوشه پروژه و خارج از مسیر بکاپ قبلی.
- [ ] بررسی ساختار آرشیو و تعداد فایل‌ها.
- [ ] محاسبه SHA-256 و بررسی دوباره checksum.
- [ ] استخراج آزمایشی به پوشه موقت مستقل و مقایسه manifest/هش فایل‌ها.
- [ ] ثبت گزارش بازیابی و مسیر دقیق فایل‌ها.
- [ ] نگهداری بکاپ اصلی مادر دو به‌صورت immutable و نگهداری نسخه جدید کنار آن.

### محدودیت اجرایی ثبت‌شده
در زمان ثبت این سند، دسترسی مستقیم به filesystem خصوصی Termux در این نشست وجود ندارد. بنابراین آرشیو محلی جدید هنوز ساخته یا restore-test نشده است. هیچ ادعایی مبنی بر به‌روزرسانی موفق بکاپ محلی مجاز نیست تا خروجی واقعی Termux و checksum/restore test ثبت شود.

## 3. خط قرمزهای غیرقابل‌مذاکره
- ظاهر تأییدشده سایت، رنگ‌ها، فونت، فاصله‌ها، چیدمان، متن، تصاویر، انیمیشن‌ها و رفتار اجزا بدون اجازه صریح تغییر نمی‌کند.

- هیچ merge، deploy، تغییر دیتابیس، افزودن Provider یا فعال‌سازی عمومی بدون تأیید جداگانه انجام نمی‌شود.
- بکاپ مادر دو اولیه دست‌نخورده باقی می‌ماند.
- هر تغییر باید کوچک، قابل بازگشت، دارای شواهد تست و ثبت در changelog باشد.
