# 14 — طراحی توسعه‌پذیر موتور مکالمه و سیاست‌های MAVIS

**وضعیت:** Design v1.0؛ فاز قراردادها و Mock Core پیاده‌سازی و آزمون شده (2026-11-09). Route عمومی، UI، ذخیره تاریخچه و Provider واقعی عمداً فعال نیستند.  
**قلمرو:** Public MAVIS در فاز اول؛ قابلیت استفاده مجدد در Private با policy و مجوز مستقل  
**اصل طراحی:** توسعه‌پذیری از طریق قراردادهای کوچک و پایدار؛ نه ساخت abstractionهای بی‌مصرف.

## وضعیت پیاده‌سازی 2026-11-09

هسته مستقل Provider در مسیرهای `src/lib/mavis/{contracts,errors,mock-provider,public-chat,public-policy}.mjs` ایجاد شده است. این هسته فقط یک use case قابل آزمون است؛ هنوز endpoint، UI، session store، retrieval-to-answer pipeline یا ارسال داده به مدل ندارد. `MAVIS_PUBLIC_ENABLED=false` پیش‌فرض است. فعال‌کردن flag به‌تنهایی هیچ Route یا قابلیت عمومی ایجاد نمی‌کند.

در use case مکالمه، غربالگری قطعی فوریت پیش از Provider اجرا می‌شود: سیگنال فوری به وضعیت ESCALATED می‌رود و Provider فراخوانی نمی‌شود؛ موضوعات دارای اولویت بررسی انسانی نیز پاسخ مولد دریافت نمی‌کنند. این غربالگری مهلت را محاسبه نمی‌کند و تشخیص حقوقی نیست.

برای پرسش‌های عادی نیز مسیر پاسخ به بازیابی منبع اولیه تأییدشده وابسته است: فقط رکوردهای verified_primary از میزبان‌های رسمی مجاز و با تاریخ دسترسی معتبر به Provider می‌رسند؛ هر ادعا باید شناسه رکورد منبع داشته باشد و سرور citation را از داده معتبر می‌سازد. نبود منبع تأییدشده، شناسه نامعتبر یا خروجی فاقد استناد، بدون فراخوانی/نمایش پاسخ مولد به بررسی انسانی برمی‌گردد. با وضعیت فعلی کتابخانه که هیچ رکوردی تأیید کامل نشده، پاسخ مولد عملاً مسدود می‌ماند.

## 1. تصمیم معماری پیشنهادی

الگوی منتخب: Modular Monolith + Ports and Adapters مطابق سند معماری 02. موتور مکالمه درون همین ساختار به ماژول‌های مستقل تقسیم می‌شود. در MVP سرویس جداگانه یا microservice ساخته نمی‌شود.

دو مسیر بررسی‌شده:
- **مسیر A: منطق یکپارچه در کامپوننت/Route Handler.** شروع سریع‌تر، اما سیاست‌ها، UI، Provider و منطق حقوقی به هم گره می‌خورند و توسعه بعدی پرهزینه می‌شود.
- **مسیر B: هسته ماژولار با قراردادهای کوچک.** کمی طراحی اولیه بیشتر، اما امکان افزودن Provider، حوزه حقوقی، زبان، کانال ارتباطی و ابزار جدید بدون بازنویسی هسته فراهم می‌شود.

**انتخاب: مسیر B**؛ چون نیازهای آینده MAVIS از ابتدا چندقلمرویی و چندمرحله‌ای است. برای جلوگیری از پیچیدگی، فقط abstractionهایی ساخته می‌شوند که حداقل دو مصرف‌کننده واقعی یا یک مرز امنیتی روشن دارند.

## 2. مرزهای ماژول

- **conversation:** پیام‌ها، شناسه مکالمه، وضعیت و تاریخچه محدود.
- **intake:** جمع‌آوری حداقل اطلاعات اولیه و رضایت.
- **triage:** تشخیص نشانه‌های فوریت و ارجاع؛ بدون تشخیص حقوقی قطعی.
- **policy:** تصمیم اینکه چه نوع پاسخ/ابزار/داده‌ای در این مرحله مجاز است.
- **knowledge:** کارت‌های دانشی نسخه‌دار و منابع پشتیبان.
- **retrieval:** بازیابی منابع بر اساس scope و مجوز؛ در MVP می‌تواند adapter ساده یا غیرفعال باشد.
- **orchestration:** ترتیب اجرای use caseها و ترکیب خروجی‌ها.
- **provider:** اتصال به مدل از طریق Port؛ Mock در توسعه.
- **handoff:** آماده‌سازی خلاصه برای تحویل انسانی، بدون ارسال خودکار.
- **observability:** شناسه رهگیری، خطا و معیارهای حداقلی بدون ثبت محتوای حساس.

هیچ ماژولی نباید مستقیماً به جزئیات داخلی ماژول دیگر دسترسی پیدا کند؛ ارتباط از طریق توابع/قراردادهای عمومی محدود انجام شود.

## 3. قرارداد ورودی مکالمه

ورودی داخلی پیشنهادی (مفهومی، نه API نهایی):
- scope: یکی از public یا private
- channel: مانند website، admin یا کانال‌های آینده
- conversationId: شناسه opaque؛ هرگز به‌تنهایی مجوز نیست
- actor: هویت و نقش تأییدشده سمت سرور؛ در Public ناشناس/محدود
- message: متن پاک‌سازی و محدودشده
- locale: در MVP مقدار fa-IR
- consent: وضعیت رضایت متناسب با عملیات
- metadata: فقط فیلدهای allowlist؛ بدون داده حساس آزاد

کلاینت اجازه ارسال systemPrompt، policyOverride، مجوز ابزار، نقش و شناسه پرونده را ندارد.

## 4. خروجی استاندارد موتور

خروجی داخلی باید مستقل از UI و Provider باشد:
- status: answered، needs_input، escalate، refused یا unavailable
- message: متن قابل نمایش
- reasonCode: کد داخلی کنترل‌شده، بدون افشای جزئیات امنیتی
- nextAction: اقدام پیشنهادی از allowlist
- citations: ارجاعات ساخت‌یافته در صورت وجود منبع معتبر
- disclaimer: برچسب/توضیح نقش در صورت نیاز
- requestId: شناسه رهگیری سمت سرور

UI فقط همین خروجی محصولی را نمایش می‌دهد؛ نباید خودش سیاست حقوقی یا تصمیم امنیتی بگیرد.

## 5. خط لوله پردازش

1. اعتبارسنجی ساختار، اندازه و نرخ درخواست.
2. تعیین scope و actor از سمت سرور.
3. کنترل رضایت لازم برای جمع‌آوری/انتقال داده.
4. اجرای triage فوریت پیش از مکالمه عادی.
5. بارگذاری policy نسخه‌دار همان scope.
6. ساخت context فقط از منابع مجاز همان scope.
7. انتخاب use case و در صورت نیاز Provider از طریق Port.
8. اعتبارسنجی خروجی و کنترل policy پس از تولید.
9. تعیین پاسخ، درخواست اطلاعات محدود یا ارجاع انسانی.
10. ثبت رویداد حداقلی و پاسخ استاندارد.

اگر triage فوریت را تشخیص دهد، مسیر عادی نباید بتواند تصمیم ارجاع را override کند.

## 6. State Machine عمومی

وضعیت‌های اولیه:
- GREETING
- DISCOVERY
- URGENCY_CHECK
- GENERAL_GUIDANCE
- HANDOFF_OFFERED
- HANDOFF_PREVIEW
- COMPLETED
- ESCALATED

قواعد:
- مسیر فوریت می‌تواند از هر وضعیت به ESCALATED منتقل شود.
- HANDOFF_PREVIEW فقط پس از رضایت صریح و آماده‌سازی خلاصه حداقلی قابل ورود است.
- COMPLETED به معنی قبول پرونده یا ایجاد رابطه وکیل-موکل نیست.
- کاربر باید بتواند مکالمه را متوقف کند یا از پاسخ به پرسش غیرضروری صرف‌نظر کند.
- خطا یا نبود Provider نباید به جعل پاسخ یا خروجی ساختگی منجر شود.

## 7. قرارداد Policy

هر policy باید داده‌محور، نسخه‌دار و قابل تست باشد و حداقل شامل این مفاهیم باشد:
- id, version, scope, status
- trigger: شرط قابل مشاهده و محدود
- decision: allow، limit، ask، escalate یا deny
- constraints: سقف داده، ابزار و نوع پاسخ
- responseGuidance: راهنمای سبک پاسخ، نه متن پنهان غیرقابل ممیزی
- sourceRefs: منابع/تصمیم‌های پشتیبان
- effectiveFrom, reviewAt
- tests: شناسه سناریوهای پذیرش

Policyهای Public و Private جدا هستند. Policy عمومی هرگز با پارامتر ارسالی کلاینت ضعیف یا جایگزین نمی‌شود.

## 8. قرارداد کارت دانشی

کارت دانشی باید schema پایدار و مستقل از محل ذخیره داشته باشد:
- id, version, title, domain
- pillar: یکی از هفت ستون تحقیق
- claim: ادعای دقیق و محدود
- summary: خلاصه قابل استفاده
- evidenceLevel: سطح شواهد
- sources[]: عنوان، ناشر، تاریخ، URL، نوع منبع و تاریخ دسترسی
- jurisdiction: مانند IR، UK، US یا GENERAL
- transferability: مستقیم، تطبیقی یا صرفاً الهام طراحی
- allowedUses[], prohibitedUses[]
- exampleDialogue: نمونه فارسی
- safetyNotes[]
- reviewStatus: draft، reviewed، approved، expired
- reviewedBy, reviewedAt, nextReviewAt
- testCases[]

کارت approved نشده نباید در رفتار عملیاتی استفاده شود. منبع حقوقی ایران و پژوهش تطبیقی باید صریحاً از هم جدا بمانند.

## 9. توسعه‌پذیری بدون بازنویسی

| قابلیت آینده | محل توسعه | بخش‌هایی که نباید تغییر کنند |
|---|---|---|
| Provider جدید | adapter جدید برای AI Provider Port | policy و use case |
| حوزه حقوقی جدید | domain pack و کارت‌های دانشی | orchestration پایه |
| کانال جدید | delivery/channel adapter | منطق دامنه |
| زبان جدید | locale pack و آزمون زبانی | مجوز و امنیت |
| ابزار جدید | Tool Registry با manifest | تصمیم نهایی policy |
| پنل مدیریت دانش | adapter و UI داخلی | schema کارت |
| اتصال WhatsApp | channel adapter و consent gate | هسته Public |
| دستیار خصوصی | use case و policy خصوصی جدا | policy عمومی |

## 10. امنیت و جداسازی

- Public و Private دارای policy، context، storage و مجوز مستقل‌اند.
- هیچ داده پرونده خصوصی در context عمومی قرار نمی‌گیرد.
- متن کاربر و اسناد، داده غیرقابل اعتمادند؛ دستورهای داخل آن‌ها policy یا system prompt را تغییر نمی‌دهند.
- ابزارها allowlist، schema ورودی، timeout، سقف اجرا و سطح ریسک دارند.
- عملیات دارای اثر بیرونی فقط پس از تأیید انسانی اجرا می‌شوند.
- log پیش‌فرض metadata حداقلی است؛ محتوای خام مکالمه یا سند محرمانه log نمی‌شود.
- rate limit، محدودیت اندازه، کنترل origin/CSRF متناسب با نوع endpoint و مدیریت خطا الزامی‌اند.

## 11. فازبندی پیاده‌سازی

### فاز 0 — همگام‌سازی و baseline
- دریافت نسخه‌های فعلی اسناد معماری و شاخه Intake.
- حل اختلاف شاخه‌ها بدون حذف تغییرات محلی.
- بررسی package scripts، lockfile و نسخه runtime.
- ثبت تست baseline.

### فاز 1 — قراردادها و تست
- [x] اعتبارسنجی پیام ورودی با allowlist و ردکردن prompt، role، scope و history ارسالی کلاینت.
- [x] تاریخچه محدود فقط از ورودی trusted سمت سرور پذیرفته می‌شود؛ persistence هنوز وجود ندارد.
- [x] خطاهای استاندارد و پاسخ عمومی بدون افشای جزئیات داخلی.
- [x] Provider Port مبتنی بر dependency injection؛ Mock هیچ ادعای حقوقی تولید نمی‌کند و بدون claim معتبر به بررسی انسانی برمی‌گردد.
- [x] feature flag خاموش به‌صورت پیش‌فرض، کنترل نام Provider و سقف خروجی.
- [x] تست واحد و lint در CI.
- [x] State Machine عمومی با مسیر فوریت غیرقابل override، حالت پایانی و preview handoff نیازمند رضایت صریح و خلاصه محدود، همراه تست انتقال‌ها.
- بدون اتصال Provider واقعی یا Route عمومی.

### فاز 2 — Public Policy MVP
- triage محدود فوریت.
- policy پاسخ عمومی و مرز خدمات اختصاصی.
- Mock Provider فقط برای آزمون قرارداد است و پاسخ حقوقی تولید نمی‌کند.
- ارجاع انسانی و preview؛ بدون ارسال خودکار.

### فاز 3 — دانش و سناریوها
- ساخت ۲۰ تا ۳۰ کارت نسخه اول.
- اتصال کارت‌ها به سناریو و تست.
- کنترل منبع، تاریخ بازبینی و تأیید انسانی.

### فاز 4 — Private Foundation
- احراز هویت، RBAC، جداسازی پرونده، audit و retention.
- فقط پس از آزمون امنیتی وارد داده واقعی شود.

## 12. معیار پذیرش

- تغییر Provider نیازمند تغییر use case یا UI نباشد.
- هیچ ورودی کلاینت نتواند scope، role یا policy را ارتقا دهد.
- هر انتقال State Machine تست مثبت و منفی داشته باشد.
- مسیر فوریت از مسیر عادی مستقل و قابل آزمون باشد.
- هیچ کارت Draft/Expired در پاسخ عملیاتی استفاده نشود.
- Public نتواند به ابزار یا داده Private دسترسی یابد.
- خروجی Mock فاقد claim است؛ پاسخ واقعی فقط با منبع اولیه تأییدشده و شناسه استناد معتبر پذیرفته می‌شود.
- عدم دسترسی به Provider با پاسخ ساختگی جبران نشود.
- handoff بدون preview و رضایت اجرا نشود.
- lint، test و build با شواهد واقعی ثبت شوند.

## 13. مواردی که هنوز تصمیم نهایی نیستند

- انتخاب schema validation library پس از بررسی dependencyهای موجود.
- انتخاب storage برای کارت‌های دانشی پس از بررسی ساختار دیتابیس و RLS.
- شکل نهایی streaming؛ در MVP غیرفعال تا تست runtime.
- تعریف دقیق نشانه‌های فوریت با بازبینی وکیل.
- Provider عملیاتی؛ نیازمند بررسی جداگانه eligibility و privacy.
- تصمیم درباره نگهداری تاریخچه Public؛ پیش‌فرض MVP حداقل‌سازی و عدم ذخیره غیرضروری.
