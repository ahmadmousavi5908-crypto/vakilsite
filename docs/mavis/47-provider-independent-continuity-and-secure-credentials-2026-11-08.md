# 47 — تداوم خدمت MAVIS مستقل از سهمیه توکن و دسترس‌پذیری Provider
تاریخ: 2026-11-08
وضعیت: الزام معماری پیشنهادی برای تصویب و پیاده‌سازی؛ هنوز قابلیت اجرایی production محسوب نمی‌شود.

## 1. اصل غیرقابل مذاکره
**سهمیه توکن، اعتبار مالی یا دسترس‌پذیری یک مدل زبانی نباید کل MAVIS را متوقف کند.** مدل زبانی یک قابلیت قابل تعویض در لایه هوشمندی است؛ منبع حقیقت داده، گردش‌کار، Intake، دانش ساختاریافته، مجوزها و ثبت سوابق نباید به مدل یا حافظه مکالمه آن وابسته باشند.

این الزام به معنی تضمین کار در زمان قطع اینترنت، خرابی دیتابیس، انقضای همه credentialها یا قطعی کل میزبان نیست. این خرابی‌ها دامنه و راهکار جداگانه دارند و باید صادقانه از هم تفکیک شوند.

## 3. معماری لایه‌ای و مستقل

### 3.1 System of Record
منبع حقیقت، دیتابیس عملیاتی و فایل‌های نسخه‌دار و تأییدشده‌اند؛ نه prompt، تاریخچه چت، vector store یا حافظه Provider. رکوردهای Intake، رضایت‌ها، وضعیت کار، منابع حقوقی، نسخه‌ها، audit و تنظیمات عملیاتی باید با شناسه پایدار ذخیره شوند.

### 3.2 Deterministic Workflow Engine
فرم‌ها، قواعد شرطی، اعتبارسنجی، چک‌لیست‌ها، مجوزها، محاسبه سهمیه، وضعیت job، شماره پیگیری و گردش‌کار تأیید با کد معمولی و قواعد نسخه‌دار اجرا شوند. برای این امور فراخوانی LLM ممنوع/غیرضروری است.

### 3.3 Knowledge Gateway
Gateway از کتابخانه حقوقی موجود و registry واحد استفاده می‌کند. جست‌وجوی exact، فیلتر metadata و PostgreSQL full-text باید بدون LLM قابل اجرا باشند. اگر embedding یا reranker در آینده اضافه شد، فقط بهینه‌ساز اختیاری است؛ نبود آن نباید جست‌وجوی پایه را از کار بیندازد.

پاسخ بدون LLM می‌تواند:
- عنوان، شناسه، مرجع، متن ثبت‌شده، تاریخ/نسخه و وضعیت را نمایش دهد؛
- منابع مرتبط را با ترتیب قواعد قطعی مرتب کند؛
- بخش‌هایی را که منبع اولیه/اعتبار جاری آن‌ها تأیید نشده مشخص کند؛
- لینک به متن اصلی و ارجاع دقیق ثبت‌شده ارائه کند.

پاسخ بدون LLM نباید وانمود کند تحلیل حقوقی، تفسیر، تطبیق موضوع با پرونده یا نظر وکیل تولید کرده است.

### 3.4 Optional Intelligence Provider
LLM از طریق interface مستقل و adapter قابل تعویض فراخوانی می‌شود. Provider، مدل، سقف‌ها و قابلیت‌ها در registry پیکربندی نگهداری می‌شوند؛ secretها در آن registry ذخیره نمی‌شوند. Use Case نباید به نام یا SDK یک Provider خاص گره بخورد.

## 4. وضعیت‌های Provider و ماشین حالت

وضعیت‌های حداقل:
- `available`: مجاز، سالم و زیر سقف.
- `degraded`: latency یا خطای گذرا؛ retry محدود.
- `quota_exhausted`: سقف توکن/اعتبار/درخواست تمام شده.
- `temporarily_unavailable`: timeout، خطای شبکه یا 5xx.
- `disabled_by_policy`: خاموش به دلیل سیاست، کشور، consent یا تنظیم مدیر.
- `credentials_invalid`: کلید نامعتبر/منقضی یا دسترسی لغوشده.
- `circuit_open`: مدارشکن فعال.
- `unknown`: وضعیت قابل تشخیص نیست؛ فراخوانی جدید محافظه‌کارانه متوقف می‌شود.

هنگام دریافت 401/403، quota/billing error یا خطای صریح policy:
1. از retry تکراری و پرهزینه جلوگیری شود.
2. خطا با request_id و کد طبقه‌بندی‌شده ثبت شود؛ secret و متن حساس ثبت نشود.
3. Provider به حالت مناسب برود و circuit breaker اعمال شود.
4. کارهای deterministic و Intake ادامه یابند.
5. وظایف LLM-dependent به صف `waiting_for_provider` بروند یا مسیر جایگزین امن نشان دهند.
6. بازیابی Provider با health check ارزان و کنترل‌شده انجام شود؛ نه فراخوانی آزمایشی پرهزینه برای هر کاربر.

## 5. ماتریس رفتار سه بازو در حالت بدون LLM

### Public Intake
- فرم کامل و شرطی، بدون تولید سؤال توسط مدل، بر اساس decision tree نسخه‌دار اجرا شود.
- پاسخ‌ها با schema و قواعد سمت سرور اعتبارسنجی و در صورت رضایت/مبنای قانونی لازم ذخیره شوند.
- چک‌لیست مدارک از قواعد تأییدشده موضوع/مرحله پرونده تولید شود.
- کد پیگیری و رسید ثبت درخواست مستقل از Provider صادر شود.
- اگر ذخیره‌سازی امن در دسترس نیست، فرم نباید ادعای ثبت موفق کند؛ داده محرمانه در localStorage یا مرورگر به‌عنوان صف پنهان ذخیره نشود. مسیر تماس جایگزین فقط با توضیح مقصد و رضایت مستقل ارائه شود.
- هیچ تحلیل یا توصیه حقوقی به‌صورت fallback تولید نشود.

### Lawyer Copilot
- جست‌وجوی کتابخانه، فیلتر بر اساس تاریخ اعتبار/نوع منبع/حوزه و نمایش متن و citation ثبت‌شده ادامه یابد.
- در نبود LLM، تحلیل مولد، پیش‌نویس استدلال و جمع‌بندی پرونده متوقف یا به صف بررسی انسانی منتقل شود.
- نتیجه retrieval به‌وضوح «فهرست منابع بازیابی‌شده، نه نظر حقوقی» برچسب بخورد.
- منابع نامعتبر، قدیمی یا فاقد اعتبارسنجی اولیه از منبع معتبر جدا نمایش داده شوند.

### Growth Intelligence
- جمع‌آوری داده مجاز، محاسبه تغییرات، گزارش دوره‌ای از داده موجود، کنترل URL و محاسبات قطعی ادامه یابد.
- پیشنهاد متنی هوش مصنوعی در صف بماند؛ گزارش داده خام و قواعد ثابت قابل ارائه باشد.
- هیچ انتشار، تغییر SEO، ارسال اعلان یا اقدام بیرونی در fallback خودکار انجام نشود.

## 6. صف، پایداری و بازیابی کارها
- Jobهای LLM-dependent با `job_id`، نوع کار، نسخه ورودی، وضعیت، زمان ایجاد/آخرین تلاش، تعداد تلاش، خطای طبقه‌بندی‌شده و idempotency key ثبت شوند.
- وضعیت‌های پیشنهادی: `queued`, `running`, `waiting_for_provider`, `needs_human_review`, `completed`, `failed_permanent`, `cancelled`.
- retry فقط برای خطاهای transient و با backoff محدود، jitter، سقف تلاش و سقف هزینه مجاز است.
- quota exhaustion نباید retry زمان‌بندی‌شده بی‌نهایت بسازد.
- با بازگشت Provider، فقط jobهای مجاز و هنوز معتبر با اولویت‌بندی و سقف concurrency پردازش شوند.
- ورودی هر job immutable/versioned باشد؛ تغییر سند یا مجوز باید پیش از اجرای مجدد دوباره بررسی شود.
- نتیجه تکراری با idempotency کنترل شود.
- عملیات دارای اثر بیرونی همچنان به تأیید انسانی نیاز دارد.

## 7. کنترل توکن و هزینه
- سقف سخت روزانه/ماهانه و سقف جدا برای هر بازو، workspace، کاربر و نوع کار تعریف شود.
- پیش از فراخوانی، تخمین محافظه‌کارانه input/output و سقف کار بررسی شود.
- یک reserve کوچک برای کارهای حیاتیِ از پیش مصوب می‌تواند تعریف شود، اما reserve نباید از سقف کل عبور کند یا باعث هزینه پنهان شود.
- وقتی 80% سقف مصرف شد هشدار؛ در 100%، درخواست‌های اختیاری LLM متوقف شوند.
- اولویت با وظایف حیاتی و مجاز، نه کاربر پرمصرف یا درخواست‌های طولانی‌تر.
- token usage، provider cost و نتیجه واقعی در ledger ثبت شود؛ اگر Provider usage را برنگرداند، مقدار تخمینی با برچسب estimated ذخیره شود.
- cache فقط برای محتوای عمومی/غیرحساس و مجاز؛ cache مشترک داده خصوصی ممنوع.
- هیچ Provider ثانویه‌ای بدون ارزیابی رسمی، مجوز جغرافیایی، قرارداد/حریم خصوصی، هزینه، نگهداری داده و رضایت لازم به‌صورت خودکار فعال نشود.

## 8. گذرواژه‌ها، کلیدها و اعتبارنامه‌ها

**MAVIS نباید گذرواژه‌های اشخاص را در کتابخانه دانش یا پرونده‌های محتوایی نگهداری کند.**

تفکیک لازم:
1. رمز عبور کاربر/وکیل: فقط سامانه احراز هویت معتبر، به‌صورت hash امن؛ MAVIS نباید متن رمز را بخواند یا بازیابی کند.
2. API key و service credential: در secret manager یا محیط امن سرور؛ رمزنگاری در حالت سکون و انتقال، دسترسی محدود، rotation، revoke و ثبت audit.
3. OAuth refresh/access token: فقط در مخزن امن credential با scope حداقلی و انقضا/لغو قابل مدیریت؛ نه در جدول دانش و نه در prompt.
4. تنظیمات غیرمحرمانه مانند نام Provider، مدل، endpoint مجاز و سقف‌ها: در config/DB بدون secret.
5. backup: secrets فقط در صورت نیاز واقعی، با رمزنگاری و سیاست بازیابی مستقل؛ هرگز در آرشیو عمومی، Git یا manifest قابل انتشار.

قواعد اجرایی:
- هیچ password، API key، cookie، recovery code یا token در log، analytics، GitHub، prompt، خروجی مدل یا داده آموزشی داخلی قرار نگیرد.
- دسترسی به secret از طریق server-side secret broker و هویت workload انجام شود؛ UI فقط وضعیت «متصل/نامعتبر/نیازمند تمدید» را نشان دهد.
- MAVIS نباید گذرواژه حساب‌های Google، Bing، Supabase، هاست یا شبکه‌های اجتماعی را جمع‌آوری کند. اتصال‌ها با OAuth رسمی یا API key محدود و قابل لغو انجام شوند.
- هیچ دسترسی به secret به معنی مجوز اقدام نیست؛ مجوز عملیات جداگانه و human approval لازم است.
- در صورت compromise: revoke، rotate، بررسی audit، ابطال نشست‌ها و incident report اجرا شود.

## 9. تفکیک اختلال‌ها
- **LLM quota exhausted:** فقط قابلیت مولد متوقف؛ deterministic workflows ادامه.
- **Provider outage:** همان رفتار quota با وضعیت degraded/unavailable.
- **Database unavailable:** ثبت و بازیابی رکوردهای جدید تضمین‌شده نیست؛ Intake نباید موفقیت کاذب نشان دهد. read-only cache فقط برای داده عمومی و با تاریخ اعتبار قابل نمایش است.
- **Search index unavailable:** exact/DB full-text fallback؛ اگر منبع اصلی در دسترس نیست، وضعیت ناقص اعلام شود.
- **Secret manager unavailable:** اتصال جدید Provider fail-closed؛ اطلاعات secret از cache ناامن خوانده نشود.
- **Internet/host outage:** سرویس آنلاین در دسترس نیست؛ این معماری ادعای offline کامل ندارد. برای نیاز واقعی offline باید بعداً deployment محلی مستقل، sync امن و threat model جدا طراحی شود.

## 10. معیارهای پذیرش اجباری

1. با Mock provider و سهمیه صفر، فرم Intake کامل، شرطی و ذخیره‌سازی آزمایشی با موفقیت انجام شود.
2. با quota exhausted، هیچ درخواست retry loop یا هزینه جدید ساخته نشود.
3. در حالت Provider unavailable، جست‌وجوی واژگانی کتابخانه و نمایش منبع/نسخه/citation ادامه یابد.
4. Copilot بدون LLM، متن retrieval را به‌عنوان نظر حقوقی معرفی نکند.
5. Growth بتواند شاخص‌های قطعی را بدون LLM محاسبه و گزارش کند.
6. Jobهای منتظر پس از بازیابی Provider فقط یک بار و با کنترل مجوز اجرا شوند.
7. درخواست‌های لغوشده/منقضی/فاقد consent پس از بازیابی اجرا نشوند.
8. هیچ secret در client bundle، Git diff، log، error response یا prompt ظاهر نشود.
9. RLS و API authorization برای anon، user نامجاز، نقش مجاز و نقش دارای scope محدود تست شوند.
10. خرابی DB یا secret manager با پیام درست و بدون موفقیت کاذب مدیریت شود.
11. تغییر Provider ثانویه بدون policy/consent/region approval غیرممکن باشد.
12. تمام رفتارهای fallback در UI فارسی و RTL با توضیح محدودیت و زمان ثبت/پیگیری روشن نمایش داده شوند.

## 11. تصمیم‌های باز پیش از پیاده‌سازی
- secret manager نهایی بر اساس پلتفرم استقرار انتخاب شود؛ تا آن زمان interface انتزاعی و env server-only در محیط توسعه.
- صف در MVP می‌تواند با PostgreSQL job table + worker idempotent شروع شود؛ انتخاب سرویس جدا فقط با نیاز throughput/availability.
- SLA و RPO/RTO باید با بودجه و توان میزبانی تعیین شوند؛ عدد خیالی درج نشود.
- ذخیره Intake بدون DB یا حالت offline واقعی تا زمان طراحی مستقل مجاز نیست.
- fallback Provider دوم، مدل محلی یا on-prem فقط پس از ارزیابی کیفیت فارسی/حقوقی، امنیت، مجوز، latency و هزینه.
- این سند به‌تنهایی مجوز افزودن Provider، هزینه، secret، migration یا فعال‌سازی production نیست.

## 12. نتیجه
MAVIS باید یک سامانه workflow و دانش با قابلیت هوشمندسازی اختیاری باشد، نه یک wrapper دور API مدل. سهمیه توکن تمام می‌شود؛ داده معتبر، فرم، قواعد، منابع، وضعیت کار و مسیر انسانی نباید به همراه آن ناپدید شوند.
