# 24 — پروتکل آماده‌سازی و تحویل یک‌مرحله‌ای Termux
تاریخ: 2026-11-08
وضعیت: قرارداد تحویل؛ اسکریپت نهایی پس از تثبیت baseline و artifact ساخته می‌شود.

## هدف
کاربر فقط یک دستور نهایی را در Termux اجرا کند. اسکریپت باید خودش مسیر پروژه را پیدا کند، پیش‌نیازها را بررسی کند، نسخه فعلی را حفظ کند، بسته دقیق را دریافت و اعتبارسنجی کند و تغییرات را یک‌بار و بدون تکرار دستی اعمال کند.

## اصول غیرقابل نقض
- اجرای دوباره همان دستور نباید باعث تکرار migration، کپی مخرب، commit تکراری یا از بین رفتن تغییرات شود (idempotent).
- پیش از هر تغییر: تشخیص workspace، git root، branch، HEAD، status، فایل‌های modified/untracked و وجود processهای فعال.
- اگر working tree دارای تغییرات ناشناخته/تأییدنشده باشد، اسکریپت بدون دست‌کاری متوقف شود و گزارش دقیق بدهد.
- از `reset --hard`، `git clean`، force push، حذف فایل و overwrite بی‌قیدوشرط استفاده نشود.
- بکاپ محلی جدید پیش از اعمال ساخته شود؛ Mother Two اصلی هرگز تغییر نکند.
- بسته از release/artifact مشخص با SHA-256 مورد انتظار دریافت شود؛ اعتبارسنجی قبل از استخراج الزامی است.
- فایل‌ها ابتدا در staging directory استخراج و بررسی شوند؛ سپس با allowlist فایل‌ها و بررسی hash مبنا اعمال شوند.
- هر فایل موجود فقط وقتی تغییر کند که hash فعلی دقیقاً با hash مبنای اعلام‌شده منطبق باشد؛ در غیر این صورت توقف امن.
- migration فقط پس از تأیید schema و فرمان جداگانه اجرا شود؛ نصب dependency فقط در صورت تغییر lockfile و با نسخه Node/npm سازگار.
- اجرای build/test با ثبت exit code و log؛ در صورت شکست، rollback از snapshot جدید یا توقف با حفظ وضعیت قابل بازیابی.
- خروجی نهایی شامل backup path، archive checksum، branch/commit، فایل‌های تغییرکرده، تست‌ها، نتیجه و دستور rollback باشد.

## رفتار فرمان واحد
1. Preflight و شناسایی محیط Termux، Node/npm/Git/Python و مسیر پروژه.
2. بررسی تطبیق repository remote و branch؛ عدم فرض مسیر ثابت.
3. بررسی clean/dirty state و قفل اجرای هم‌زمان.
4. ساخت backup کامل workspace شامل tracked، modified و untracked؛ حذف secrets از گزارش، نه از backup محلی امن.
5. دانلود artifact versioned از GitHub Release یا آدرس ثابت commit؛ عدم استفاده از URL شناور مانند latest.
6. بررسی checksum، manifest، inventory و نسخه artifact.
7. استخراج در پوشه staging موقت و بررسی path traversal، symlink ناخواسته و فایل خارج از allowlist.
8. مقایسه hashهای مبنا؛ dry-run داخلی و گزارش تغییرات.
9. اعمال اتمیک فایل‌ها با نگهداری نسخه قبلی.
10. اجرای فقط تست‌های لازم و قابل‌اجرا؛ build با `--webpack` در Termux.
11. در شکست، rollback خودکار فقط به snapshot ایجادشده در همین اجرا و فقط اگر rollback امن باشد؛ در غیر این صورت توقف بدون پاک‌سازی.
12. نوشتن گزارش JSON و log فارسی/انگلیسی قابل پیگیری.

## کانال تحویل
اولویت: GitHub Release یا artifact versioned با checksum ثابت و دسترسی عمومی، چون repository عمومی است و نیازی به قرار دادن token در فرمان Termux نیست. اگر artifact خصوصی شد، احراز هویت باید از gh auth موجود استفاده کند و هرگز token داخل متن فرمان یا فایل مخزن نوشته نشود.

## معیار پذیرش قبل از تحویل به کاربر
- اجرای آزمایشی روی یک کپی از workspace با Node/Git مشابه Termux.
- اجرای دوباره دستور بدون تغییر اضافی و بدون تکرار عملیات.
- آزمون dirty working tree و اثبات توقف امن.
- آزمون checksum اشتباه و اثبات عدم استخراج/اعمال.
- آزمون فایل موجود با hash متفاوت و اثبات عدم overwrite.
- آزمون شکست build و اثبات امکان بازگشت.
- بررسی نهایی دستور واحد: کوتاه، copy-paste، بدون نیاز به نصب دستی ابزارهای متعدد یا اجرای چندباره.
- هیچ‌گاه پیش از اجرای این تست‌ها، فرمان به‌عنوان «آماده و تضمین‌شده» معرفی نشود.

## محدودیت محیط
GitHub connector می‌تواند کد و مستندات remote را ایجاد کند، اما به Termux گوشی و workspace محلی دسترسی مستقیم ندارد. بنابراین hash، backup و test نهایی محیط محلی فقط پس از اجرای فرمان واحد روی دستگاه قابل تأیید است. فرمان باید این بررسی‌ها را خودش انجام دهد و از کاربر خروجی‌های پراکنده نخواهد.
